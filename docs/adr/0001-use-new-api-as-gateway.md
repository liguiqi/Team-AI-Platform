# ADR-0001 使用 NEW-API 作为统一模型网关

## 状态
Accepted

## 日期
2026-04-03

## 背景
本项目需要尽快落地一个“内部可用、可治理、可运维”的 AI 对话平台。需求并不要求自研对话 UI 或网关，而是要求以最少定制成本完成以下目标：

- 隐藏官方采购的上游 API Key。
- 提供浏览器可访问的聊天界面。
- 支持模型映射、额度控制、限流与日志审计。
- 支持本地和单机生产环境的快速部署。

如果直接让前端调用上游 API，会带来密钥泄露和治理缺失的问题；如果自研网关和前端，则会显著拉长落地周期。

## 决策驱动因素
- 首期必须优先保证智谱链路打通。
- 方案必须以配置和脚本为主，而不是源码大改。
- 管理员必须能够在后台完成渠道和 token 管理。
- 普通用户必须只接触聊天界面，不接触供应商 API Key。
- 本地与生产需要尽量共用同一套结构。

## 备选方案

### 方案 A：前端直接调用智谱
优点：
- 实现快。

缺点：
- 上游密钥暴露在前端或终端。
- 无统一限流、日志和治理。
- 后续新增供应商会导致前端配置复杂化。

结论：
- 放弃。

### 方案 B：自研网关 + 自研前端
优点：
- 自主可控。

缺点：
- 实施成本高。
- 首期周期过长。
- 对本项目“快速落地整合平台”的目标不匹配。

结论：
- 放弃。

### 方案 C：NEW-API 作为网关，LibreChat 作为前端
优点：
- 两个组件都已有成熟生态。
- `NEW-API` 提供渠道、token、额度、限流、日志、模型映射等治理能力。
- `LibreChat` 提供现成聊天 UI。
- 基本可以通过配置和脚本完成整合，不需要 fork 第三方源码。

缺点：
- 需要理解两个系统之间的配置边界。
- 需要自行处理配置渲染、管理员账号和联调流程。

结论：
- 采用。

## 最终决策
- 使用 `NEW-API` 作为统一模型网关。
- 使用 `LibreChat` 作为最终用户对话入口。
- 官方采购的上游密钥只进入 `.env` 和 `NEW-API` 渠道配置。
- LibreChat 只持有 `NEW_API_SERVICE_TOKEN`。
- 本地与生产都采用 Docker Compose 编排。

## 决策细化

### 为什么不是让 LibreChat 直连智谱
因为 LibreChat 更适合做用户界面，而不是承担供应商治理、限流、日志与多渠道配置工作。把供应商接入逻辑放在 `NEW-API` 中，职责更清晰。

### 为什么模型要做别名映射
为了让前端只看到平台批准暴露的模型名，例如 `zhipu-primary`，而不是直接绑定某个真实上游模型名如 `glm-4-flash`。这样后续替换真实模型时，前端无需改动。

### 为什么要脚本化 bootstrap
因为首次初始化如果完全依赖管理员在后台手工点击，会导致：
- 可重复性差
- 环境不一致
- 出错后难以回放

所以本项目将 root 初始化、限流、渠道配置、服务 token 创建统一交给 `scripts/bootstrap-new-api.sh`。

## 后果

### 正面后果
- 前后端职责清晰。
- 安全边界明确。
- 供应商接入与前端体验解耦。
- 后续新增供应商时优先改 `NEW-API` 配置而不是改 LibreChat。
- 运维可通过脚本与后台双轨处理问题。

### 负面后果
- 运维人员需要同时理解 LibreChat 和 `NEW-API` 两套系统。
- 配置同步变得重要，尤其是 `NEW_API_SERVICE_TOKEN` 和管理员密码。
- 某些初始化步骤需要在脚本中处理第三方系统的细节差异。

## 当前结论
在本项目的交付目标、时间成本和治理要求下，`NEW-API + LibreChat` 是最合适的组合。后续若要演进到更复杂的平台，也应优先在当前网关模式上扩展，而不是回退到前端直连上游的方案。
