# 需求说明

## 文档目的
本文档用于明确本仓库的业务目标、技术边界、实施范围、角色分工和验收前提。它不是市场 PRD，而是面向实施者、验收人和后续运维人员的工程需求基线。后续的架构、部署、运维、验收文档均以本文为准。

## 背景
公司已经采购上游大模型服务，希望在内部提供统一的 AI 对话入口。实际落地时存在三个核心问题：

1. 采购得到的上游 API Key 不能直接出现在浏览器、前端仓库或普通用户终端。
2. 不同部门同学需要一个可直接使用的对话界面，而不是手工调用 OpenAI 兼容 API。
3. 系统必须具备基础治理能力，包括模型映射、额度控制、限流、日志审计、备份恢复和可复现部署。

为满足以上要求，本项目采用 `NEW-API + LibreChat` 组合，将上游能力统一收口到 `NEW-API`，再由 `LibreChat` 提供最终用户对话界面。
在用户身份侧，新增 `Casdoor` 作为统一认证层，用于承接邮箱与手机号真实认证，再通过 OIDC 把登录结果回传给 LibreChat。

## 项目目标

### 总目标
构建一个可在本地和单机云服务器上稳定运行的内部 AI 对话平台，首期以智谱作为主验收渠道，后续能够平滑扩展到其它模型提供商。

### 具体目标
- 使用 `NEW-API` 统一管理上游渠道、模型映射、服务 token、额度与限流。
- 使用 `Casdoor` 统一管理手机号、邮箱、验证码与 OIDC 登录。
- 使用 `LibreChat` 作为对话前端，给内部用户提供浏览器可用的聊天界面。
- 让 LibreChat 能动态同步 `NEW-API` 当前授权模型列表，并支持前端展示白名单。
- 将真实上游密钥仅保存在服务端环境变量和 `NEW-API` 渠道配置中。
- 建立完整的脚本体系，覆盖初始化、启动、停止、重启、健康检查、联调、备份、恢复、密钥检查。
- 建立完整中文文档，覆盖需求、架构、部署、运维、验收和管理员操作。

## 使用场景

### 场景 1：普通员工通过网页发起对话
普通员工打开 LibreChat 页面，先通过 Casdoor 完成邮箱或手机号真实认证，再在 `API-zhipu` / `API-deepseek` / `API-aliyun` / `API-kimi` 等供应商分组下选择平台允许暴露的模型，输入问题后得到对话结果。用户不持有供应商密钥，只使用平台已经开放的模型集合。

### 场景 2：管理员新增或调整模型渠道
管理员登录 `NEW-API` 后台，查看渠道配置、额度和日志，必要时替换上游密钥、调整模型映射、禁用异常渠道或修改限流参数。

### 场景 3：平台运维进行启动、联调与恢复
管理员在新机器或故障机器上，根据文档执行 `make init`、`make up`、`make smoke-zhipu`、`make backup`、`make restore`，完成平台部署或恢复。

### 场景 4：管理员只想让前端显示部分模型
管理员在 `.env` 中配置 `LIBRECHAT_VISIBLE_MODELS` 或供应商模型同步规则，随后执行 `make sync-provider-models`，让 LibreChat 按供应商分组展示最新模型子集。

## 范围定义

### In Scope
- 根仓结构与目录规范。
- 本地与生产单机 Docker Compose 编排。
- `NEW-API` 接入智谱原生 `ZhipuV4` 渠道。
- `Casdoor` 接入邮箱 SMTP 与阿里云 `PNVS SMS`。
- `LibreChat` 通过 `NEW-API` 的 OpenAI 兼容接口访问模型。
- 本地环境内置 LibreChat Admin Panel，用于角色与权限管理。
- 服务 token、限流配置、模型映射自动化。
- LibreChat OIDC state / session 跨重启持久化。
- 备份恢复、健康检查、联调、诊断、密钥校验脚本。
- 面向管理员和验收人员的完整中文文档。

### Out of Scope
- 自研模型推理服务。
- Kubernetes 首发版本。
- 企业级 SSO、LDAP、组织权限体系定制。
- 深度二开 LibreChat 或 NEW-API 源码。
- 复杂计费、结算和多租户隔离。

## 功能需求

### 启停与初始化
- 本地必须支持 `make init`、`make up`、`make down`、`make restart`。
- 生产必须支持 `MODE=prod bash scripts/up.sh` 等等效操作。
- 初始化时自动生成本地随机密钥，减少手工输入。

### 网关治理
- `NEW-API` 必须作为唯一模型网关。
- 必须支持智谱 `ZhipuV4` 渠道。
- 必须支持 DeepSeek、阿里云百炼与 Kimi OpenAI 兼容渠道。
- 必须支持智谱全量 19 个模型（13 chat + 6 vision）。
- 必须支持服务 token、可选模型白名单与多模型矩阵。
- 必须支持模型请求限流配置。
- 必须支持自动 bootstrap，一键完成部署。

### 前端对话
- LibreChat 必须可访问。
- Casdoor 必须可访问。
- 用户必须能通过邮箱或手机号完成真实认证。
- LibreChat 必须只通过 `NEW-API` 自定义端点访问模型。
- LibreChat 必须支持从 `NEW-API /v1/models` 动态获取模型列表。
- Casdoor 登录页必须支持 light / dark 自适应，并屏蔽当前不用的 `WebAuthn` / `Face ID` 登录方式。
- LibreChat 重启后，OIDC 链路不应长期停留在 state 校验失败页。
- LibreChat 必须支持网络搜索功能（Serper + Firecrawl + Jina）。

### 运维能力
- 必须具备应用层健康检查脚本。
- 必须具备主链路 smoke test 和智谱真实联调脚本。
- 必须具备 DeepSeek、阿里云百炼与 Kimi 真实联调脚本。
- 必须具备前端模型同步脚本。
- 必须具备备份和恢复脚本。
- 必须具备基础敏感信息扫描能力。
- 必须支持 systemd 开机自启动。

## 非功能需求

### 一致性
- 本地与生产的目录结构、Compose 组织方式、脚本行为尽量一致。
- 文档必须与脚本实现保持一致，不能出现“文档说可以、脚本做不到”的状态。

### 可复现
- 新机器在具备 Docker 与 Compose 的前提下，应能按文档复现。
- 版本必须固定，不允许使用 `latest`。

### 可维护
- 尽量使用官方镜像与外置配置。
- 非必要不修改第三方源码。
- 所有关键动作优先通过脚本完成，而不是依赖临时人工操作。

### 安全
- 真实密钥不得进入 Git。
- 浏览器端不得直接持有上游供应商密钥。
- 浏览器端不得直接持有短信、邮箱服务端密钥。
- 运维脚本和文档中不得要求用户把真实密钥写入仓库跟踪文件。

## 安全与合规要求
- `ZHIPU_API_KEY`、`DEEPSEEK_API_KEY`、`ALIYUN_API_KEY`、`KIMI_API_KEY` 只允许出现在本地或生产环境变量、容器环境与 `NEW-API` 渠道配置中。
- 短信与 SMTP 凭据只允许出现在本地或生产环境变量、Casdoor 配置与容器环境中。
- LibreChat 只持有 `NEW_API_SERVICE_TOKEN`，不持有智谱官方采购密钥。
- LibreChat 默认关闭本地邮箱登录，避免绕过统一认证。
- `.env`、运行时数据目录、备份包必须在 `.gitignore` 中忽略。
- 敏感配置变更后，必须重新渲染 LibreChat 配置并重启相关容器。

## 工程约束
- 平台首期必须以智谱链路打通为第一优先级。
- 编排方式固定为 Docker Compose，不引入额外编排系统。
- 管理员操作必须尽量集中在 `NEW-API` 后台和仓库脚本，不依赖复杂的手工数据库编辑。
- 运维文档必须可直接供接手人员使用。

## 验收前提
- 用户提供真实可用的 `ZHIPU_API_KEY`。
- 本地机器可访问智谱上游地址。
- 本地 `13000`、`3080` 端口可用。
- 运行机器已安装 Docker Engine 与 Docker Compose v2。

## 成功标准
- `NEW-API` 管理后台可访问。
- LibreChat 页面可访问。
- `make up` 后自动 bootstrap 完成，平台立即可用。
- `NEW-API /v1/models` 能返回当前智谱、DeepSeek、阿里云百炼与 Kimi 渠道同步后的模型集合。
- LibreChat 中可见所有授权模型，并能完成一次真实问答。
- 网络搜索功能在 LibreChat 中可用。
- 所有容器内存使用在限制范围内。
- 文档、脚本、Compose、环境变量模板形成闭环。
